Hardware / Firmware Co-Simulation — Explainer & Reference

DDR-Style Delay-Line Training: How the Firmware Talks to the RTL, and Where It Breaks

A ground-up walkthrough of a small but real C-firmware-drives-Verilog-RTL co-simulation project: what each file does, how the binary-search training algorithm works with actual numbers, and the two genuine bugs — one already fixed, one still open — that this project surfaced.

Project: ddr_training_project Files covered: delay_line.v · tb_top.v · training_fw.c · golden_model.py Status: off-by-one RTL bug fixed · tap-31 firmware bug open

§1 Overview

What this project actually is, in plain terms, before any code.

Real DDR memory has a problem: the electrical signal that carries data arrives at the memory controller slightly early or slightly late depending on temperature, voltage, and manufacturing variation in that specific chip. To read the data correctly, the controller has to nudge its internal sampling clock by a small, adjustable delay so it samples right in the middle of the "good" window — this is called eye centering or DDR training, and it runs every time the system boots, before the memory is trusted for anything else.

This project is a small, working, from-scratch model of one axis of that process. It is not a real DDR PHY — it is a teaching-scale stand-in built to practice one very specific and very real skill: writing bare-metal-style C firmware that drives real Verilog hardware in simulation, before any physical chip exists, and being able to tell, when something goes wrong, whether the bug is in the firmware or in the hardware.

The analogy in one sentence Firmware doesn't know where the "good" delay setting is. It has to discover it by trying settings and asking hardware "did that one work?" — exactly like a real PHY training routine, just with a single adjustable number (0–31) standing in for the analog timing margin.

Four pieces work together:

  • A hidden pass/fail window [LO, HI] on a 5-bit delay code (0–31) — this is the "chip's" actual timing margin, picked before each run and written to a config file. Firmware never gets to read this file; it only finds out about the window by querying.
  • Real Verilog RTL (delay_line.v) that holds that hidden window and answers pass/fail for whatever delay code it's given, with a genuine one-clock-cycle register latency — just like real hardware.
  • Real C firmware (training_fw.c) that runs a binary-search algorithm to discover the window purely by querying, the same way production PHY training firmware would.
  • An independent Python "golden model" (golden_model.py) that already knows the hidden window and computes the correct answer directly, with zero shared code — used purely to grade whether firmware got the right answer.

The interesting part isn't the RTL (it's deliberately tiny) or the firmware (it's a textbook binary search). The interesting part is the seam between them — the exact place a real verification or firmware engineer spends their time — and the two genuine bugs that seam exposed, which sections §8 and §9 walk through with real reproduced output.

§2 Architecture

Two separate OS processes, synchronized by two named pipes, with the Verilog side running as a real event-driven simulation.

training_fw (compiled C) and vvp sim.vvp (the compiled Verilog simulation) are two completely separate programs running at the same time. They don't share memory or call each other's functions — they only exchange plain decimal integers, one per line, through two Unix named pipes (FIFOs) that stand in for the memory-mapped registers a real embedded core would use to talk to PHY hardware.

Firmware never sees window_config.txt — it only learns the window by sending delay codes and reading back pass/fail, exactly like real register-mapped hardware.

Two details make this a real hardware/firmware co-simulation rather than a mock:

  • Blocking opens act as free synchronization. A Unix FIFO's open() call blocks until the other end is also opened. So tb_top.v's $fopen("req_pipe","r") and firmware's fopen(req_pipe_path,"w") each wait for the other — no polling, no sleep(), no race condition. Both sides start in lockstep automatically.
  • The response has genuine one-cycle latency. When tb_top.v receives a delay code, it doesn't answer immediately — it waits for @(posedge clk) and lets the registered comparator in delay_line.v actually evaluate, just as a real clocked register would. Section §3 shows exactly why this matters.

§3 The hardware: delay_line.v

A single registered comparator. This is the entire DUT (device under test).

delay_line.v
module delay_line (
    input  wire        clk,
    input  wire [4:0]  delay_setting,   // the value firmware is trying
    input  wire [4:0]  lo,              // low edge of the passing window
    input  wire [4:0]  hi,              // high edge of the passing window
    output reg         pass             // registered pass/fail result
);
    always @(posedge clk) begin
        pass <= (delay_setting >= lo) && (delay_setting <= hi);
    end
endmodule

That's the whole design. lo and hi are set once at the start of simulation (from window_config.txt) and never change during a run. Every clock edge, the module looks at whatever delay_setting firmware has currently applied and registers a fresh pass/fail decision one cycle later.

The comment in the real file is explicit about what's not modeled: a real PHY delay tap is an actual chain of analog delay elements feeding a phase comparator against a physical timing margin. Here, that whole physical process is replaced by a direct inequality check against a hidden [lo, hi] window. The simplification is deliberate — the point of this project is the co-simulation plumbing and the training algorithm, not analog fidelity.

Why the one-cycle latency matters

Because pass is assigned with <= inside always @(posedge clk), the result for a given delay_setting is only visible one clock edge after that setting was applied — not combinationally, instantly. tb_top.v respects this by explicitly waiting @(posedge clk) before reading pass back (see §4). This is a small thing, but it's exactly the kind of timing behavior that trips up co-simulation setups that try to shortcut it.

One full clock cycle separates "firmware applies a setting" from "hardware's answer is valid" — exactly why tb_top.v waits for a clock edge before reading pass back.

§4 The testbench harness: tb_top.v

The "hardware side" server loop. Loads the hidden window, then serves one request at a time forever.

Stripped to its logic, ignoring the boilerplate:

tb_top.v
reg [4:0] lo = 0;
reg [4:0] hi = 31;

// 1. read the hidden window once, at time 0
got = $fscanf(cfg_fd, "%d %d", lo, hi);

// 2. open the pipes -- BLOCKS until firmware opens the other end
req_fd  = $fopen("req_pipe",  "r");
resp_fd = $fopen("resp_pipe", "w");

// 3. serve requests forever, until firmware sends 255 ("quit")
forever begin
    got = $fscanf(req_fd, "%d", code);
    if (code == 255) begin $finish; end

    delay_setting = code[4:0];
    @(posedge clk);   // let the register actually update
    #1;               // let the non-blocking assignment settle

    $fdisplay(resp_fd, "%0d", pass);
    $fflush(resp_fd);
end

Three things worth calling out:

  • The protocol is deliberately dumb. Every message on both pipes is a plain decimal integer, one per line — 0–31 on the way in (a delay code), 0 or 1 on the way out (fail/pass), and the sentinel 255 means "I'm done, please $finish." No binary framing, no headers.
  • window_config.txt is read exactly once, at time 0, before the pipes even open. This is what lets run_all.py test five different hidden "chips" back-to-back without recompiling the RTL — each run just rewrites the text file before launching a fresh vvp process.
  • Every query is logged on both sides. tb_top.v prints TB: received delay_setting=X -> pass=Y (window is [lo,hi]) for every single request. This log is the other half of the triage technique in §8 — comparing what firmware thinks it asked against what hardware says it received.

The full run also dumps training.vcd — every signal's value over time, in the standard Value Change Dump format that waveform viewers like GTKWave read. Section §7 walks through exactly that file.

§5 The firmware: training_fw.c

Three functions. One does all the hardware talking; the other two are a textbook binary search built on top of it.

Firmware's entire view of the hardware is one function:

training_fw.c — query_pass()
static int query_pass(int delay) {
    fprintf(req_fp, "%d\n", delay);   // send the candidate setting
    fflush(req_fp);

    int result = -1;
    fscanf(resp_fp, "%d", &result);   // BLOCK until hardware answers
    query_count++;
    return result;
}

Every other function in the file is built entirely on top of this one call — this is "the seam," the exact point where a real firmware implementation would swap named-pipe I/O for reads/writes to a memory-mapped register. Nothing above this function needs to know or care how the answer was actually obtained.

The overall strategy in main() is three steps:

  1. Find any one setting that passes, starting from nothing (find_any_passing_value).
  2. Binary-search left from that point down to the first passing value (find_left_edge).
  3. Binary-search right from that point up to the last passing value (find_right_edge).

The trained center is then just the midpoint of [left, right].

5.1 — find_any_passing_value(): get one foothold

Binary search for an edge needs to start from a value you already know passes. This function's job is purely to find one such value, by probing outward from the middle of the whole legal range (0–31):

training_fw.c — find_any_passing_value() (current, unfixed version)
static int find_any_passing_value(int lo, int hi) {
    int mid = lo + (hi - lo) / 2;
    for (int offset = 0; offset <= (hi - lo) / 2; offset++) {
        if (mid - offset >= lo && query_pass(mid - offset)) return mid - offset;
        if (mid + offset <= hi && query_pass(mid + offset)) return mid + offset;
    }
    return -1;  // nothing in range passes
}

For the full range [0,31], mid = 15. It checks 15, then 14 and 16, then 13 and 17, walking outward one step at a time until something passes. This is a linear probe, not a binary search — the project's own KNOWN_LIMITATIONS.md is upfront about this being the least efficient part of the algorithm, and §9 shows exactly how this loop's boundary condition also hides a real bug.

5.2 — find_left_edge(): binary search for the first PASS

training_fw.c
static int find_left_edge(int lo, int hi) {
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (query_pass(mid)) hi = mid;
        else                 lo = mid + 1;
    }
    return lo;
}

This is the standard "find the first true in a sorted false…false,true…true sequence" pattern. It's called as find_left_edge(MIN_DELAY, known_good) — it already knows known_good passes, so it only has to search the region below it. Every iteration halves the search space: check the midpoint, and either the true left edge is at or below it (hi = mid) or strictly above it (lo = mid + 1).

5.3 — find_right_edge(): the mirror image

training_fw.c
static int find_right_edge(int lo, int hi) {
    while (lo < hi) {
        int mid = lo + (hi - lo + 1) / 2;   // note the +1
        if (query_pass(mid)) lo = mid;
        else                 hi = mid - 1;
    }
    return lo;
}

Same idea, searching upward from known_good. The +1 in the midpoint calculation is not a typo — it's what keeps this loop from getting stuck when lo and hi are adjacent (without it, mid could equal lo forever when the range has exactly two elements). This is the classic paired idiom: round down when searching for a left edge, round up when searching for a right edge.

Both edge-search functions are each O(log n) — for a 32-value range that's at most 5 queries per edge, which is what makes this fast enough to run at every boot on real hardware. Section §6 traces both functions with the exact numbers from a real run.

§7 Reading your waveforms

Your three GTKWave screenshots are all the same [10,22] run from §6 — just viewed with different number formats and zoom. Here is exactly what each signal means and how it lines up with the query log above.

Before the screenshots: the five signals GTKWave is showing are the exact ports of delay_line.v from §3, dumped straight from the testbench's internal dut instance:

  • clk — the free-running simulation clock (period 10 ns, from always #5 clk = ~clk; in tb_top.v).
  • delay_setting[4:0] — the candidate value firmware just sent over req_pipe. This changes every time tb_top.v services a new request.
  • hi[4:0] and lo[4:0] — the hidden window, loaded once from window_config.txt and constant for the whole run. In this run: lo=10, hi=22.
  • pass — the registered comparator output. Note it updates one clock edge after delay_setting changes, exactly as described in §3's timing diagram.
How to read any future run yourself Every value on the delay_setting trace, read left to right, is one call to query_pass() in the firmware — the waveform is the query log, just drawn instead of printed. Cross-reference it against the fw_debug_stderr_*.txt log (or, live, the FW: query delay=... lines) and against the tb_debug_*.txt hardware-side log to do exactly the bug triage in §8.

§8 Bug #1 (fixed): the RTL off-by-one

A one-character bug in the comparator, and the exact triage process that proved it was hardware's fault, not firmware's.

Earlier in this project's history, delay_line.v's comparator was written with the wrong operator on the lower bound:

Buggy version 
pass <= (delay_setting > lo) && (delay_setting <= hi);   // > instead of >=
Correct version (what ships today) 
pass <= (delay_setting >= lo) && (delay_setting <= hi);

The effect: the lower bound of every window was excluded instead of included. Running the full 5-config suite against the buggy version, all five failed — every reported left edge came back exactly one higher than expected (hidden window [10,22] trained as [11,22], and so on).

The triage: is it firmware, or is it hardware?

This is the actual diagnostic process, and it generalizes to almost any firmware/RTL mismatch:

  1. Reproduce deterministically. Same config, same wrong answer, every time — rules out a timing race or nondeterministic bug.
  2. Check the firmware-side query log at the failing boundary: FW: query delay=10 -> fail.
  3. Cross-reference the hardware-side log for the same query: TB: received delay_setting=10 -> pass=0 (window is [10,22]).
  4. Both sides agree on what happened. Firmware asked about 10 and correctly reported that hardware said "fail." That rules out a firmware bug and rules out a pipe/communication bug — the transport worked perfectly.
  5. Conclusion: hardware computed the wrong answer for an input that, per the spec (lo=10 should be inclusive), should have passed. That's an RTL bug, not a firmware bug.
Why this triage step matters The failure looked like it could be either side — firmware trained the wrong window, which is exactly what a firmware logic bug would also produce. The only way to tell them apart was comparing both sides' logs for the exact same query and confirming they agreed with each other but disagreed with the spec. When both logs agree, the bug is upstream of both logs — in this case, in the comparator's Verilog itself.

After changing > to >= and rebuilding, delay=10 correctly returns pass=1 and all five configs pass — this is the state the project is in today (delay_line_KNOWN_GOOD.v.bak is kept alongside the live delay_line.v specifically so this bug/fix story stays reproducible).

§9 Bug #2 (open): tap 31 is unreachable

A genuine algorithmic bug in find_any_passing_value()'s loop bound — reproduced live, right now, for this document. Not yet fixed in the code you have.

Current state This bug is still present in your training_fw.c. Nothing in this project's files has been changed to fix it — this section only explains and demonstrates it.

Where the bug lives

Recall find_any_passing_value() from §5.1:

static int find_any_passing_value(int lo, int hi) {
    int mid = lo + (hi - lo) / 2;
    for (int offset = 0; offset <= (hi - lo) / 2; offset++) {
        if (mid - offset >= lo && query_pass(mid - offset)) return mid - offset;
        if (mid + offset <= hi && query_pass(mid + offset)) return mid + offset;
    }
    return -1;
}

For the full range lo=0, hi=31: mid = 15, and the loop's upper bound is (31-0)/2 = 15 — integer division, which truncates. So offset only ever reaches 15, meaning the farthest tap this function can ever check on the high side is mid + 15 = 30. Tap 31 — the very top of the legal range — can never be queried, no matter what.

Green = every tap this function can reach for the full range [0,31]. Red = tap 31, structurally unreachable no matter how many offsets run.

There's a second, smaller issue in the same loop: at offset = 0, both if statements check mid - 0 and mid + 0 — the same value, 15, twice. Harmless (it just wastes one query), but worth fixing alongside the main issue.

Proof: reproduced live, right now

To confirm this is real and not just a theoretical read of the code, I rebuilt this exact project (your unmodified training_fw.c and delay_line.v) and ran it with the hidden window set to window_config.txt = "31 31" — the narrowest possible legal window, sitting exactly on the unreachable tap:

FW:   query delay=15 -> fail
FW:   query delay=15 -> fail   ← offset 0, checked twice
FW:   query delay=14 -> fail
FW:   query delay=16 -> fail

And the hardware-side log for the same run, filtered for the taps that matter, confirms tap 31 was never even sent — this isn't a case of hardware answering wrong, it's a case of firmware never asking:

Live run — tb_debug (unedited, grepped)
TB:   received delay_setting=30 -> pass=0  (window is [31,31])
TB:   received delay_setting=29 -> pass=0  (window is [31,31])
TB:   received delay_setting=0  -> pass=0  (window is [31,31])
TB:   received delay_setting=30 -> pass=0  (window is [31,31])
TB: got quit, exiting
(no line for delay_setting=31 exists anywhere in this run's log)

The RTL is completely innocent here: delay_setting=31 against a window of [31,31] would correctly evaluate (31>=31) && (31<=31) = pass if it were ever asked. It's never asked. Firmware gives up and reports TRAINING FAILED for a window that is, in fact, perfectly valid — a false negative purely from the search loop's own boundary math.

Same triage skill as §8, opposite conclusion Run the same checklist as the RTL bug: reproduce deterministically ✓ (every run with a window touching 31 fails the same way) → check firmware's log (never asks for 31) → check hardware's log (never receives 31) → both logs agree, and this time what they agree on is that the query never happened. That points squarely at firmware's search-loop bound, not the comparator.

The shape of a fix (not applied here)

The core idea — should you or someone else choose to apply it later — is to size the loop bound off the larger of the two distances from the midpoint to each end of the range, not off (hi-lo)/2 in the direction it happens to be checking:

int left_distance  = mid - lo;
int right_distance = hi  - mid;
int max_offset = (left_distance > right_distance) ? left_distance : right_distance;
// for [0,31]: mid=15, left_distance=15, right_distance=16, max_offset=16 → offset 16 reaches tap 31

Checking the midpoint once, outside the loop, before starting offset at 1 instead of 0 also removes the duplicate query noted above. This document intentionally stops at explaining the shape of the fix — nothing in your actual project files has been modified.

§10 Known limitations

Straight from the project's own KNOWN_LIMITATIONS.md — honest notes on what a production version would do differently.

  1. The initial foothold search is linear, not binary. This is bug #2's home in §9 — cheap near the middle of the range (9 queries for [10,22]), expensive near the edges (31–33 queries for [0,3] or [27,31]). A real implementation would likely start from a last-known-good value saved from the previous boot, or use a coarse-then-fine two-pass search.
  2. One-dimensional, not two-dimensional. Real DDR5 read/write centering sweeps delay and voltage reference together. This project only models the time axis, to keep the co-simulation plumbing simple.
  3. The "hardware" is one registered comparator, not a real delay chain. delay_line.v models the outcome of a pass/fail decision directly rather than an actual chain of programmable delay elements feeding a phase comparator. Deliberate simplification, not a claim of physical accuracy.
  4. No per-bit deskew or multi-lane modeling. Real DDR training handles multiple data bits independently after coarse centering; this project trains exactly one lane.
  5. Named pipes stand in for a register interface. Real firmware would talk to hardware via memory-mapped registers, not FIFOs. Pipes give real, blocking, unbuffered synchronization between two OS processes without needing a full instruction-set simulator or DPI-C bridge.
  6. No timeout/retry logic. A production training algorithm bounds every search with a maximum iteration count in case hardware never reports a sane result. This version assumes hardware always responds — fine for a simulation you control, a real robustness gap in production firmware.
